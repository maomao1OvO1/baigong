URL ビルダー

1 行目にベースアドレス、以降は 1 行に 1 つ `key=value`。完成した URL と、各値のエンコード前後が並びます。
手で組んだ URL が壊れるのはエンコードのせいです。値に `&` が入ると黙って 2 つのパラメータになり、`#` が入ると以降が丸ごと飲み込まれます。

よくある質問

空白は %20 と + のどちらにすべき？

値がどこで解釈されるかによります。application/x-www-form-urlencoded として解析されるクエリ文字列では `+` が空白を意味しますが、パス部分やフラグメント、自前でデコードする API では `+` はただのプラス記号です。どちらの規約かは受け取る側しか知らないため、切り替えを用意しています。

元の URL にあったパラメータが再エンコードされないのはなぜ？

意図的です。デコードして再エンコードするのは往復になりません。既存の値の `+` は本物の空白になり、すでにエンコード済みの値は**二重エンコード**され、署名やトークンがその場で壊れます。既存のパラメータはバイト単位でそのまま通し、新しく追加した分だけをエンコードします。

どの文字をエンコードする必要がありますか？

予約文字です。`&` はパラメータの区切り、`=` はキーと値の区切り、`#` はフラグメントの開始、`?` はクエリの開始、`%` はエスケープの導入です。空白・プラス・非 ASCII 文字も実際の経路では安全ではありません。サーバーやプロキシ、ログ基盤がそこで URL を切ることがあります。本ツールは該当する値を個別に指摘します。
